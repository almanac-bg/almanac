Куиз битки в реално време за много играчи: играй на **[almanac.bg](https://almanac.bg)**. Тук е пълният изходен код
на играта, свободен софтуер под [AGPL-3.0](LICENSE).

![АЛМАНАХ](apps/web/public/og.jpg)

Какво има:

- **Режими:** соло тренировка, дневно предизвикателство, класирани дуели 1 на 1 и отбори 2 на 2, мачове всеки срещу
  всеки за 3 и 5 играчи, Роял за 8 играчи с отпадане, частни стаи за приятели и линкове с предизвикателство, които
  всеки може да изиграе.
- **Прогрес:** профилите качват нива, отключват аватари, рамки и титли, печелят постижения, изпълняват дневни
  задачи, трупат дневна серия (с щитове), изкачват се в месечни сезони и пазят подробна статистика.
- **Приятели и общност:** играчите могат да се добавят за приятели, да се канят и предизвикват, да искат реванш и да
  предлагат свои въпроси за одобрение. Посетителите могат да играят веднага като гости и да запазят прогреса си
  по-късно.

## Бърз старт

Нужен е Node 24+. Играта ползва вградения `node:sqlite`, така че няма база данни за инсталиране.

```bash
npm install
npm run dev
```

Отвори http://localhost:5173, регистрирай профил и играй. При разработка **първият профил, който регистрираш, става
администратор**, за да може да одобрява въпроси от общността. В продукция никой не става администратор с
регистрация; виж стъпка 7 от [Внедряване](#внедряване-произволен-vps--docker).

Истинската банка с въпроси на играта (около 2000 въпроса) не е част от публичния код, за да не могат отговорите да се
търсят по време на мач. Без нея се играе с примерните 120 въпроса от `apps/server/src/data/questions.sample.json` —
публична извадка от истинската банка, която стига за разработка и за всички тестове. Виж [Въпроси](#добавяне-на-въпроси).

Когато никой друг не чака за мач, след няколко секунди ботове заемат празните места, така че всеки режим може да се
играе и без други хора. За да тестваш истински мултиплейър локално, отвори втори браузър (или частен прозорец) с друг
профил.

| Скрипт              | Какво прави                                                                |
| ------------------- | -------------------------------------------------------------------------- |
| `npm run dev`       | API + realtime сървър на :3001 и Vite на :5173 (през proxy)                |
| `npm run build`     | Билдва уеб приложението и пакетира сървъра в `apps/server/dist`            |
| `npm start`         | Продукционен сървър на :3001 (чист Node), който сервира и уеб приложението |
| `npm run typecheck` | Проверява типовете във всички пакети                                       |
| `npm test`          | Всички тестове (около минута и половина), виж по-долу                      |
| `npm run lint`      | Форматиране, правила и подредба на импортите (Biome), както в CI           |
| `npm run format`    | Поправя автоматично каквото може от горното                                |

### Тестове

`npm test` пуска тези тестове с вградения test runner на Node:
- **`e2e.test.ts`** стартира истински сървър с временна база данни и минава през всичко с истински сокети. Двама
  играчи и ботове покриват: соло, класиран дуел с повторно свързване, отпадания в Роял, частни стаи и отбори,
  дневното предизвикателство, приятели, покани и предизвикателства, всеки коз, въпроси от общността с модерация,
  сезонни награди, сигнали и скриване на грешни въпроси, гости, линкове с предизвикателство, реванши, отказ от
  напомнянията за серията, резултати, показани отново след прекъсната връзка, невалидни съобщения по сокета (които
  никога не бива да сриват сървъра) и кеширането на файловете на сайта.
- **`game.test.ts`** управлява енджина на мача с подменен часовник: напускане и служебни загуби, прекъснати връзки,
  изоставени мачове, „Двойно или нищо“, равенства и силата на ботовете.
- **`rewards.test.ts`** проверява какво носи класиран мач, върху истинска база: мач, напуснат преди третия въпрос,
  не се зачита, по-късното напускане носи победа според изиграното, гостите играят срещу хора без рейтинг, а лимитът
  от три мача на ден между двама казва защо рейтингът не се е променил.
- **`restart.test.ts`** покрива плавните рестарти (текущите мачове първо завършват) и опит в дневното
  предизвикателство, прекъснат от срив.
- **`database.test.ts`** проверява историята на въпросите за всеки играч и че честите заявки използват индекси.
- **`production.test.ts`** пуска сървъра като в продукция: администратори се добавят само от командния ред,
  security хедъри за браузъра, health check, отчети за сривове, заглавията и адресите на страниците, „noindex“ и 404
  за грешни адреси.
- **`maintenance.test.ts`** покрива почистването на изтекли сесии, дневните копия на базата данни и изтриването на
  профили, неизползвани три години (с писмо месец по-рано).
- **`progress.test.ts`** покрива дневните задачи, щитовете за серията, вечерното напомняне за серията, почистването
  на гост-профили и статистиката за старта.
- **`monitoring.test.ts`** проверява отчетите за грешки към Sentry, ограничението на броя им и че тунелът от браузъра
  препраща само към собствения проект на сайта.
- **`questions.test.ts`** валидира банката с въпроси. Новите въпроси трябва да минават проверката.
- **`rules.test.ts`** проверява правилата за точките и прогреса, включително границите на дните и сезоните по
  софийско време при смяна на лятното часово време.

`npm run test:dist -w @quiz/server` пуска същите тестове срещу продукционния bundle. Колко играчи носи един сървър
показва `npm run build && caffeinate -i npm run load -w @quiz/server` (няколко минути; `ulimit -n 30000` преди
големи стъпки): хиляди симулирани играчи с реалните времена на играта и колко бързо отговаря сървърът междувременно.
На MacBook с M4 3000 души наведнъж минаха без нито една грешка, с най-много 35 ms забавяне. GitHub Actions
(`.github/workflows/ci.yml`) при всеки push към `main` и всеки pull request пуска lint, typecheck, build, двата
варианта на тестовете и браузърните тестове, на Node 24 и 26; после билдва Docker образа, проверява, че стартира, и
прави пълен бекъп и възстановяване с Litestream. На `main`, щом всичко това мине, билдва образа за сървъра (ARM) и го
публикува в GitHub Container Registry като `ghcr.io/almanac-bg/almanac:<commit>` — продукцията пуска точно него.

## Как се играе

- **Режими:**
  - Соло: 10 въпроса от избрана категория.
  - Дневно предизвикателство: едни и същи 10 въпроса за всички (всеки играч получава свой ред на отговорите), един
    опит на ден, без козове, собствена класация. Гост или профил, направен днес, играе свои 10 въпроса извън
    класацията (иначе втори профил за секунди би прочел отговорите на деня); от следващия ден — общите. Опит,
    прекъснат от рестарт на сървъра, може да се изиграе отново, а напуснат на отброяването (преди първия въпрос) не
    е опит. Денят се брои за серията, ако е изиграна поне половината.
  - Дуел: 1 на 1.
  - Отбори: 2 на 2, с отбори, балансирани по рейтинг.
  - Трио: 3 играчи.
  - Арена: 5 играчи.
  - Роял: 8 играчи. Играчът с най-малко точки отпада след въпроси 3, 5, 7, 9, 11 и 13.
  - Предизвикателство (линк с предизвикателство, `/c/<id>`): играч създава линк с 10 фиксирани въпроса и го изиграва,
    преди да го сподели; всеки с линка (и гостите) играе същите въпроси веднъж, със свой ред на отговорите и без козове, и влиза в
    класацията на самия линк. Създателят получава известие за всеки резултат. Линковете важат 7 дни.
  - Частна стая: 2–8 играчи, с настройки за въпросите, таймера, категорията, отпадането и отборите.
  - При старта само Дуел и Роял са отворени като класирани опашки (`PUBLIC_QUEUES`), за да се срещат първите играчи
    помежду си, а не с ботове; Отбори, Трио и Арена се отварят, когато играта порасне (и остават достъпни в частните
    стаи).
- **Реванш:** след класиран мач с други хора всеки може да поиска реванш в рамките на минута; щом всички поискат,
  същите хора играят отново (едно „не“ или излизане прекратява предложението).
- **Точки:** 500 за верен отговор, до +500 за бързина (спрямо обичайния таймер) и +50 за всяка стъпка в серията
  от верни отговори (до +250). Бонусът за бързина започва да намалява след времето за четене на въпроса (1–3,5 с
  според дължината му): бързото четене не носи точки, нито натискането преди въпросът да е прочетен. При равен
  резултат решава броят верни отговори, после по-краткото общо време; въпрос без отговор се брои с цялото време на
  таймера.
- **Козове:** всеки има и четирите от първия си мач, така че резултатът не се решава от изиграното време; няма ги
  само в дневното предизвикателство и в линковете с предизвикателство. По един от всеки вид на мач и най-много един на
  въпрос, преди да отговориш. Какво прави всеки коз се казва извън часовника, където има време за четене: докато се
  търсят играчи, при избора на категория за Соло и в стаята, докато се чака домакинът (и в „Колекция“); отброяването
  само ги назовава. На телефон под всяка икона има дума, а коз, който не може да се изиграе, казва защо при докосване.
  С клавиатура: 1–4 за отговорите, Q, W, E, R за козовете (по мястото на клавиша, така че и на кирилска подредба).
  Ботовете играят 50/50 и „Двойно или нищо“.
  - 50/50: премахва два грешни отговора.
  - Втори шанс: дава втори опит, за половин точки.
  - Още време: дава ти 5 секунди повече.
  - Двойно или нищо: удвоява точките за един среден или труден въпрос; грешка струва 500 (никога под нулата).
- **Напускане и прекъсната връзка:** който напусне мача, се класира на последно място (по-ранното напускане е
  по-назад), освен при вече отпадналите — те запазват мястото, на което са отпаднали. Мачът свършва веднага, щом
  остане само една страна. Ако съперникът излезе преди третия въпрос, мачът не се зачита за останалите (без победа
  и без рейтинг; напусналият губи рейтинг), а по-късно победата носи XP и рейтинг според изиграната част от мача. При
  прекъсната връзка играта чака 5 секунди, преди въпрос да може да приключи без играча;
  ако 30 секунди всички хора в мача са без връзка, остатъкът от мача се изиграва веднага, все едно не са отговорили.
  Резултат, излязъл, докато играчът е офлайн, се показва при връщането.
- **Ботовете** заемат свободните места в класираните мачове след няколко секунди. Решението си за въпроса ботът
  взема, щом въпросът се отвори: когато всички хора са отговорили, ботовете отговарят веднага, с времето, което
  щяха да вземат (точките им са същите), вместо хората да чакат часовника им. Ботът играе толкова силно,
  колкото показва рейтингът му (до 1600), а рейтингът се променя по-малко срещу ботове, отколкото срещу хора (K 24
  срещу 40), така че Elo се установява там, където е реалното ниво на играча. Над 1000 мачът срещу ботове тежи все
  по-малко, а от 1600 нагоре не мести рейтинга изобщо: върхът на класацията се изкачва само срещу хора. Първите три мултиплейър мача на играча
  са срещу малко по-меки ботове. Едни и същи двама души могат да си влияят на рейтинга само три пъти на ден, а
  мачовете на гост срещу хора са без рейтинг (срещу ботове — с рейтинг). Същото важи за нов профил, докато не е на
  поне ден и няма 10 изиграни мача: срещу хора — без рейтинг, срещу ботове — с рейтинг (иначе профил за 10 секунди е
  партньор за подарени победи). В частните стаи класирането носи XP само над хора, отговорили на поне половината
  въпроси (не над ботове или прозорец, оставен отворен), и най-много 600 XP на ден; бонусът за перфектен мач е за мачове
  с поне 10 въпроса.
- **Разнообразие на въпросите:** помнят се всички въпроси, които всеки играч е виждал (до 6000); мачовете избират въпроси, нови за
  всички играчи в мача, а след тях — видените най-отдавна. Мачът започва с по-лесни и завършва с по-трудни въпроси,
  но не в строг ред: на границите лесен и среден (или среден и труден) могат да си разменят местата.
- **Защита от измами:** сървърът държи часовника, отговорите и крайния срок на всеки играч. Клиентите никога не виждат
  верния отговор преди разкриването му. Всеки отговор на човек се пази 90 дни (верен ли е и за колко време): в
  `/admin` → Игра модераторите виждат играчи, които отговарят вярно на почти всеки среден и труден въпрос за под
  2,5 с (така играе програма, която чете отговорите от копие на банката), и въпроси, при които делът верни не
  съвпада с трудността им или е толкова нисък, че отбелязаният отговор може да е грешен.
- **Сезони:** календарни месеци по софийско време. Рейтингът е отделен за всеки сезон, а в началото на новия сезон
  всеки рейтинг се връща наполовина към 1000. В края на сезона играчите получават XP и ексклузивни рамки и титли за
  най-високия ранг (Бронз → Майстор), достигнат в режим, в който имат поне 10 изиграни докрай класирани мача,
  от десетия мач нататък (нито пренесеният рейтинг, нито няколко късметлийски първи мача правят сезон; напуснат мач
  мести рейтинга, но не е от мачовете на сезона).
- **Прогрес:** всеки мач носи XP: за участие, верни отговори (според трудността), класиране, бонус за перфектна игра,
  първия мач за деня, дневната серия (расте 30 дни, с етапи на 7, 30 и 100), дневните задачи и постиженията. Ниво L
  изисква общо `50·L·(L−1)` XP. Нивата отключват аватари, рамки и титли до ниво 100.
- **Дневни задачи:** три на ден (софийско време): една за участие, една за добра игра и една за нещо различно,
  избрани за всеки играч и фиксирани за деня; XP се дава при изпълнение на всяка, плюс бонус за трите.
- **Щитове за серията:** всеки 7 дни от дневната серия носят щит (най-много 2); пропуснат ден изразходва щит, вместо
  да прекъсне серията. Играчите с потвърден имейл могат да включат вечерно писмо, когато серията им е на път да
  прекъсне (с отписване с един клик).
- **Профили:** играчите влизат с потребителско име или потвърден имейл. Незадължителният имейл (потвърждава се с
  линк) включва „Забравена парола?“: еднократен линк за нова парола, който изтича след 1 час и прекратява всички
  сесии на профила. Паролата се сменя от Настройки.
- **Гости:** „Играй като гост“ създава профил без име и парола, така че до първата игра има само едно докосване.
  Гостите играят всичко освен онова, което изисква постоянна самоличност (приятели, собствени стаи, собствени линкове
  с предизвикателство, въпроси, доклади), не се показват в класациите и могат по всяко време да запазят прогреса си
  с име и парола. Гост-профил, в който никой вече не може да влезе (не е останала сесия), се изтрива след ден.
- **Модерация:**
  - Филтърът за обидни имена покрива кирилица, латиница и leetspeak и резервира имена като admin и АЛМАНАХ.
  - Играчите могат да докладват други играчи от профила им.
  - Модераторите обработват докладите в `/admin` → Доклади: отхвърляне, смяна на името или бан за 1/7/30 дни или
    завинаги.
  - След мач играчите могат да прегледат всеки въпрос и да сигнализират за грешка. Модераторите виждат сигналите в
    `/admin` → Сигнали, подредени по брой, и могат веднага да скрият въпрос от новите мачове (и да отменят това).
    Скрит въпрос излиза и от днешното дневно предизвикателство, ако още никой с профил не го е започнал; иначе
    денят остава с него (класацията сравнява едни и същи въпроси), както и линковете, направени преди това.
  - Списъците с думи са в `apps/server/src/moderation.ts`.
- **Телефони:** сайтът се инсталира на началния екран (web app manifest с икони) и после се отваря на цял екран като
  приложение, без магазин за приложения.
- **Поверителност (GDPR):**
  - Политиката за поверителност и условията за ползване са на `/privacy` и `/terms`.
  - Играчите могат да изтеглят всичките си данни като JSON и да изтрият профила си от Настройки.
  - Шрифтовете се хостват на самия сайт и няма проследяване от трети страни.
- **Приятели:** играчите изпращат покани по потребителско име и виждат на живо кой е онлайн. Могат да поканят
  приятели в стая или да ги предизвикат на дуел 1 на 1 с един клик.
- **Въпроси от общността:** играчите от ниво 3 нагоре предлагат въпроси. Модераторите (`/admin`) ги одобряват, като
  при нужда ги редактират, или ги отхвърлят. Одобрените въпроси влизат в играта веднага, с името на автора, а авторът
  получава XP.
- **Постижения:** общо 41. Дефинициите са в `packages/shared/src/achievements.ts`, а правилата — в
  `apps/server/src/achievements.ts`.

## Добавяне на въпроси

Играчите могат да предлагат въпроси в самата игра, а администраторите ги одобряват в `/admin` — така се добавят въпроси
в играта на almanac.bg.

Банката на almanac.bg се пази в отделно частно хранилище (`almanac-questions`), клонирано тук в `private/` — папка,
която това хранилище игнорира:

```bash
git clone git@github.com:almanac-bg/almanac-questions.git private
```

Когато я има, сървърът използва `private/questions.json`, а `npm run build` я слага до сървърния bundle. Образът,
който CI публикува, е само с публичния код: в продукция `docker-compose.yml` монтира `private/` само за четене
(`QUESTIONS_PATH`), така че нови въпроси на сървъра са `git -C private pull && docker compose restart app`, без
деплой. Без банката сървърът играе с публичната извадка,
`apps/server/src/data/questions.sample.json`. Двата файла са в един и същ формат и `npm test` проверява наличните. За
да добавиш вградени въпроси, добави ги в края на банката (после commit и push в `private/`):

```json
{
  "id": "gen-031",
  "category": "general",
  "difficulty": "easy",
  "q": "Колко цвята има българското знаме?",
  "options": ["3", "2", "4", "5"],
  "answer": 0,
  "fact": "Цветовете на знамето са определени още в Търновската конституция от 1879 г.",
  "factSource": "https://bg.wikipedia.org/wiki/Национално_знаме_на_България"
}
```

`answer` е индексът на верния отговор в `options`. Отговорите се разбъркват за всеки мач. Категориите (и името им в
играта): `general` (Обща култура), `science` (Наука), `history` (История), `geography` (География), `movies` (Кино и
телевизия), `music` (Музика), `sports` (Спорт), `technology` (Технологии и игри), `literature` (Изкуство и
литература) и `nature` (Природа и животни).

`fact` е по желание: едно-две изречения „Знаеше ли?“ (до 200 знака), които играта показва след отговора — в мач
насаме с бутон „Спри, за да прочета“, а в резултатите и в прегледа на въпросите на всеки. Фактът е нещо ново около
отговора, а не самият отговор, и не подсказва друг въпрос от банката. Всеки факт има `factSource` (https) — място,
където написаното може да се провери; `npm test` пази тези правила.

## Внедряване (произволен VPS + Docker)

Стекът е от три контейнера: приложението (чист Node, със SQLite на volume), Caddy, който се грижи за HTTPS и сам
взема и подновява сертификатите от Let's Encrypt, и Litestream, който стриймва всяка промяна в базата към
S3-съвместимо object storage. Нищо не го обвързва с конкретен доставчик. **2 vCPU и 4 GB** са предостатъчни за начало:
при тест с натоварване 1000 едновременни играчи използваха около 4% от едно ядро и 160 MB памет. Всички образи
работят на x86 и ARM.

Избор на сървър (цените са към октомври 2026; провери ги преди поръчка) — в ЕС заради GDPR и ниската латентност до
България:
- **Hetzner** CX23 (5,99 €) или CAX11 (ARM, 6,49 €) във Фалкенщайн, Нюрнберг или Хелзинки: най-изгодни, когато ги
  има (от септември 2026 често са изчерпани). CPX22, който винаги може да се поръча, струва около три пъти повече.
- **netcup** VPS 500 (около 8 €, помесечно; Германия или Виена) или **OVHcloud** VPS-1 (4,49 €): добри алтернативи.

**Преди да започнеш:** в `.env` ще трябват името ти и адрес за връзка, доставчикът на имейли и хостинг доставчикът
(`OPERATOR_NAME`, `CONTACT_EMAIL`, `EMAIL_PROVIDER`, `HOSTING_PROVIDER` и т.н.; те никога не са в кода). Услугата се
поддържа от физическо лице и политиката за поверителност и условията за ползване показват тези данни; без
`OPERATOR_NAME` сървърът в продукция отказва да тръгне. Пощенски адрес (`OPERATOR_ADDRESS`) не е задължителен за
безплатна игра без реклами — ОРЗД иска име и данни за връзка, а имейлът е такъв; ако искаш да дадеш адрес, нека е
пощенска кутия, не домашният. Ако играта започне да носи приходи (реклами, плащания, дарения), Законът за
електронната търговия изисква и адрес; тогава най-чистото е фирма (напр. ЕООД с адрес на виртуален офис). И двата
документа са чернови: погрижи се да бъдат прегледани за твоя случай.

Командите по-долу са за `root` (както е при Hetzner); с друг потребител добавяй `sudo`.

Стекът извън кода: сървър при **Hetzner**, DNS и пренасочване на писмата до теб при **Cloudflare**, бекъпите при
**Cloudflare R2** (друга фирма, а не тази на сървъра: един проблем с един профил не губи и двете), имейлите на играта
през **Scaleway Transactional Email**, отчетите за грешки в **Sentry**, известията от **Better Stack**. Включи 2FA
навсякъде, включително при регистратора на домейна. Пази копие на SSH ключа за сървъра (напр. в password manager-а).

1. **Създай сървъра:** Ubuntu 24.04 или по-нов, с вход през SSH ключ (без вход с парола). Във firewall-а на доставчика разреши
   TCP 22 (в идеалния случай само от твоя IP адрес), 80 и 443 и UDP 443 (HTTP/3). Включи бекъпите на сървъра при
   доставчика (Hetzner Backups, 20% от цената): единственото копие, което някой, проникнал в сървъра, не може да изтрие.
   После автоматичните обновления за сигурност — с рестарт в тих час, когато ги изисква ново ядро, и Docker, който при
   рестарт изчаква текущите мачове да се доиграят:

   ```bash
   apt install unattended-upgrades
   cat > /etc/apt/apt.conf.d/52almanac-reboot <<'APT'
   Unattended-Upgrade::Automatic-Reboot "true";
   Unattended-Upgrade::Automatic-Reboot-WithUsers "true";
   Unattended-Upgrade::Automatic-Reboot-Time "01:30";
   APT
   mkdir -p /etc/systemd/system/docker.service.d
   printf '[Service]\nTimeoutStopSec=400\n' > /etc/systemd/system/docker.service.d/almanac-stop-timeout.conf
   printf 'X11Forwarding no\n' > /etc/ssh/sshd_config.d/60-almanac.conf && sshd -t && systemctl reload ssh
   ```

   (01:30 UTC е 03:30–04:30 софийско време. `deploy/check.sh` вдига тревога, ако рестарт чака повече от три дни.)
2. **DNS в Cloudflare** (безплатният план): добави домейна, смени nameserver-ите му при регистратора с двата, които
   Cloudflare дава, и добави записите — всички **DNS only** (сивият облак: HTTPS прави Caddy, а приложението трябва
   да вижда истинските адреси на играчите):

   | Тип  | Име   | Стойност                                              |
   | ---- | ----- | ----------------------------------------------------- |
   | A    | `@`   | IPv4 адресът на сървъра                               |
   | A    | `www` | IPv4 адресът на сървъра                               |
   | AAAA | `@`   | IPv6 адресът на сървъра                               |
   | AAAA | `www` | IPv6 адресът на сървъра                               |
   | CAA  | `@`   | `0 issue "letsencrypt.org"`                           |
   | CAA  | `@`   | `0 issue "sectigo.com"` (резервният издател на Caddy) |

   Добави и `CAA` `@` `0 iodef "mailto:postmaster@almanac.bg"` (къде издателите съобщават за отказана заявка) и
   **изключи Universal SSL** (SSL/TLS → Edge Certificates): докато записите са DNS only, той не върши нищо, а щом в
   зоната има CAA записи, Cloudflare тихо добавя свои за още шест издатели. Когато домейнът стане Active, включи
   DNSSEC (DNS → Settings) и добави DS записа при регистратора.
3. **Създай bucket за бекъпите в Cloudflare R2** (изисква начин на плащане; до 10 GB и милион записа на месец са
   безплатни — при пълна натовареност всяка секунда от денонощието това са най-много няколко евро на месец): bucket
   `almanac-backups` с **Jurisdiction: European Union**, после R2 → API Tokens → токен с **Object Read & Write**
   само за него. В `.env`: `BACKUP_ENDPOINT=https://<Account ID>.eu.r2.cloudflarestorage.com`,
   `BACKUP_REGION=auto` и ключовете от токена. (Hetzner Object Storage също работи, но е при същата фирма като
   сървъра.)
4. **Дай на сървъра достъп до частната банка с въпроси:** създай ключ без парола (за да работи `git pull` без теб) и
   добави публичния му ключ в almanac-questions → Settings → Deploy keys, само за четене (ако организацията не ги
   позволява: Organization → Settings → Repository → Deploy keys):

   ```bash
   ssh-keygen -t ed25519 -N '' -f ~/.ssh/id_ed25519 -C almanac-server
   cat ~/.ssh/id_ed25519.pub     # това отива в Deploy keys
   ssh -T git@github.com         # приеми ключа на GitHub (yes); отговорът „successfully authenticated“ е наред
   ```
5. **Инсталирай Docker и пусни приложението:**

   ```bash
   curl -fsSL https://get.docker.com | sh
   git clone https://github.com/almanac-bg/almanac.git almanac && cd almanac
   git clone git@github.com:almanac-bg/almanac-questions.git private
   cp .env.example .env        # попълни DOMAIN, OPERATOR_*, BACKUP_*, HOSTING_PROVIDER
   deploy/deploy.sh
   ```

   Деплоят тегли образа, който CI е публикувал за последния commit в `main` — на сървъра нищо не се билдва. Пакетът
   `ghcr.io/almanac-bg/almanac` е публичен (в GitHub: организацията → Packages → almanac → Package settings → Change
   visibility), така че сървърът го тегли без парола. **Запази `.env` в password manager** веднага: в него
   са ключовете за бекъпите, имейлите и Sentry, а без тях бекъпите не могат да се възстановят на нов сървър.
6. **Провери, че всичко работи:** `docker compose ps` показва три контейнера `Up` (приложението — `healthy`),
   `docker compose logs litestream` показва, че базата се реплицира, а `curl -fsS https://almanac.bg/api/health`
   отговаря с `{"ok":true}`.
7. Отвори https://almanac.bg, регистрирай профила си и го направи администратор:

   ```bash
   docker compose exec app node apps/server/dist/cli.mjs admin add <your-username>
   ```

   (`admin list` и `admin remove <username>` работят по същия начин.)
8. **Тествай бекъпа веднъж** (виж „Бекъпи“ по-долу): възстанови го до живата база и провери копието. Бекъп, който
   никога не е бил възстановяван, още не е бекъп. (CI също прави пълен бекъп и възстановяване с продукционната
   конфигурация при всяка промяна и пуска приложението върху възстановената база.)
9. **Включи отчетите за грешки:** създай безплатен профил в Sentry с организация в региона **EU** (Франкфурт; не
   може да се смени по-късно), добави проект от тип „Browser JavaScript“ и в настройките му включи „Prevent Storing
   of IP Addresses“. Сложи DSN-а му в `.env` като `SENTRY_DSN` и пусни командата за деплой отново. Оттам нататък
   грешките на сървъра и сривовете в браузърите на играчите пристигат в Sentry (и по имейл), групирани и с реда от
   кода. Без `SENTRY_DSN` нищо не се изпраща никъде.
10. **Добави проверки, които те известяват** (Better Stack, безплатният план — фирма от ЕС): монитор на
    `https://almanac.bg/api/health` на всеки 3 минути (той пада и при пълен диск: под 256 MB свободни `/api/health`
    отговаря с 503) и два „heartbeat“ монитора — дневен и седмичен. Скриптовете в `deploy/` проверяват на сървъра
    онова, което отвън не се вижда, и при успех сигнализират своя heartbeat; ако сигналът спре да идва, получаваш
    известие. Неуспешна проверка казва и защо: пингва `<URL>/fail` с причината, така че тревогата идва веднага.
    - `deploy/check.sh` (всеки ден): TLS сертификатът се подновява (валиден още поне 14 дни), дискът не е пълен,
      всички контейнери работят, рестарт за обновления не чака от дни;
    - `deploy/backup-check.sh` (всеки ден): възстановява бекъпа до живата база и проверява, че копието е цяло и
      **актуално** — приложението записва часа в базата на всеки 15 минути, затова копие, изостанало с повече от
      час, значи, че репликацията е спряла (изтекъл ключ, пълен bucket).

    ```bash
    cat > /etc/cron.d/almanac <<'CRON'
    0 6 * * * root /root/almanac/deploy/check.sh <URL на дневния heartbeat> >> /var/log/almanac-check.log 2>&1
    0 5 * * * root /root/almanac/deploy/backup-check.sh <URL на втория heartbeat> >> /var/log/almanac-check.log 2>&1
    CRON
    ```

**Имейли.** Играта праща писма за потвърждение, нова парола и напомняния за серията; писмата до адреса за контакт
трябва да стигат до теб.
1. **Изпращане — Scaleway Transactional Email** (фирма от ЕС, без чужди лога в писмата и без дневен таван; 300
   писма на месец са безплатни, после 0,25 € на 1000): Transactional Email → добави домейна `almanac.bg` и сложи в
   Cloudflare записите, които дава (DKIM, DMARC; SPF — виж т. 3). После IAM → приложение (напр. `almanac-smtp`) с
   политика **TransactionalEmailEmailFullAccess** за проекта и API ключ за него. В `.env`:
   `SMTP_URL=smtp://<Project ID>:<Secret key>@smtp.tem.scaleway.com:587`. Ключът важи най-много година: сложи си
   напомняне да го подновиш (неизпратен имейл стига и до Sentry).
2. **Получаване — Cloudflare Email Routing** (безплатно): включи го и пренасочи `privacy@almanac.bg` към пощата си;
   Cloudflare сам добавя MX записите си.
3. **SPF е един запис за целия домейн**, затова обедини двата: `v=spf1 include:_spf.mx.cloudflare.net
   include:_spf.tem.scaleway.com ~all` (провери в Scaleway дали показва точно този `include`). Ако Scaleway поиска и
   свой MX, остави този на Cloudflare: писмата до теб минават през него.
4. **Отчети за недоставени писма** (по желание, но препоръчително): адрес, от който писмата се връщат или който ги
   маркира като спам, вече не получава напомняния, а в Настройки пише защо. Сложи в `.env`
   `EMAIL_EVENTS_SECRET=$(openssl rand -hex 24)`. В Scaleway: Topics and Events → тема (fr-par) → абонамент от тип
   HTTPS към `https://almanac.bg/api/email-events/<секрета>` (приложението само потвърждава абонамента); после
   Transactional Email → Webhooks → нов webhook за домейна с тази тема и събитията `email_dropped`,
   `email_mailbox_not_found`, `email_spam` и `email_blocklisted`.

Използвай порт **587**: много доставчици (сред тях и Hetzner) блокират изходящите портове 25 и 465 на нови сървъри.

**Обновяване:** в тих час, защото опашките са затворени, докато текущите мачове се доиграят:

```bash
deploy/deploy.sh
```

Скриптът изписва часа (при нужда Litestream връща базата точно до него), дърпа двете хранилища и тегли образа, който
CI е публикувал за този commit — той съществува само ако всички проверки са минали, иначе деплоят спира, преди да
промени каквото и да е. Обновява и Caddy и Litestream (с точни версии, които Dependabot предлага да вдигнеш), пази
работещия досега образ като `almanac:previous` за бързо връщане и чисти старите образи. На сървъра нищо не се билдва.
После старата версия спира плавно: играчите в
опашката научават, че идва обновяване, нови мачове не започват, а текущите се доиграват (до ~5½ минути,
`DRAIN_SECONDS`; още незавършените тогава приключват с точките дотук). През тези няколко секунди, докато приложението
не работи, Caddy показва страница, която се презарежда сама, браузърите на играчите се свързват отново автоматично, а
отворените табове зареждат новата версия, щом играчът не е в мач.

**Връщане към предишна версия**, ако обновяването се обърка: `deploy/rollback.sh` пуска предишния образ за секунди, без
билд, а `deploy/rollback.sh <commit>` — образа на всеки по-стар commit от `main` (кодът в git остава, където е: поправи
напред или `git checkout <commit>` преди следващия деплой). Ако новата
версия е мигрирала базата само със съвместими стъпки (нова таблица или колона — `compatible` в
`apps/server/src/db.ts`), старата работи с нея, както е, а каквото не е попълнила, новата попълва при следващото си
пускане (важи от версията от 28 октомври 2026 нататък). След несъвместима стъпка старата отказва да тръгне
(„Database is at schema vN…“): преди миграции приложението записва копие на базата в
`/data/backups/quiz-vN-before-vM.db` — върни него, както дневно копие (по-долу), или възстанови от Litestream до
записания час (`restore -timestamp <часа>`).

**Когато нещо не е наред:**

```bash
docker compose ps                          # кое работи и кое не
docker compose logs -t --tail 200 app      # последните редове, с час (същото за caddy и litestream)
docker compose restart app                 # рестарт (текущите мачове се доиграват първо)
df -h /                                    # място на диска
```

**Бекъпи:** на три нива.
1. **Litestream (непрекъснато, извън сървъра):** всяка промяна стига до object storage за секунди; може да се
   възстанови всеки момент от последните 14 дни. Всеки ден `deploy/backup-check.sh` проверява, че копието е актуално.
2. **Дневни копия (автоматично, на сървъра):** след 04:00 софийско време приложението записва консистентно копие на
   базата в `/data/backups/quiz-YYYY-MM-DD.db` и пази последните 14 (`BACKUP_KEEP_DAYS`). Удобни са за бързо
   поправяне на грешка; намират се на същия диск.
3. **Бекъпите на сървъра от доставчика** (Hetzner Backups): дневни образи на целия сървър, пазени извън машината и
   изтриваеми само от профила при доставчика.

Проверка, че Litestream има бекъп (възстановява го до живата база, без да я пипа, и проверява копието):
`deploy/backup-check.sh`.

**Сървърът е изгубен** (около 45 минути, ако `.env` и SSH ключът са в password manager-а; веднъж в годината мини
по списъка на тренировка):
1. Нов сървър (стъпка 1: firewall, обновления, бекъпи) — или възстанови образ от Hetzner Backups и прескочи до 6.
2. Deploy key за частната банка (стъпка 4) и двете хранилища (стъпка 5) — **същият `.env`** от password manager-а.
3. Базата от Litestream (без `deploy/deploy.sh` преди това):

   ```bash
   docker pull ghcr.io/almanac-bg/almanac:$(git rev-parse HEAD)
   docker tag ghcr.io/almanac-bg/almanac:$(git rev-parse HEAD) almanac:latest
   docker compose run --rm --no-deps --entrypoint true app      # създава празния volume за данните
   docker compose run --rm --no-deps litestream restore -o /data/quiz.db /data/quiz.db
   deploy/deploy.sh
   ```
4. В Cloudflare смени A и AAAA записите (`@` и `www`) с адресите на новия сървър.
5. Изчакай сертификата: `curl -I https://almanac.bg` (Caddy го взема сам за минута-две след DNS промяната).
6. Cron-ът от стъпка 10 и проверка, че двата heartbeat-а в Better Stack светят зелено на следващия ден.

(За момент преди грешка добави `-timestamp 2026-10-25T14:00:00Z` към `restore`.)

Възстановяване на дневно копие (или на копието отпреди миграция):

```bash
docker compose stop app litestream
docker compose run --rm --no-deps --entrypoint sh app -c 'ls /data/backups'   # избери файл
docker compose run --rm --no-deps --entrypoint sh app -c \
  'cp /data/quiz.db /data/quiz-before-restore.db && cp /data/backups/quiz-2026-10-25.db /data/quiz.db &&
   rm -rf /data/quiz.db-wal /data/quiz.db-shm /data/.quiz.db-litestream'
docker compose up -d
```

Litestream започва нова верига от бекъпи от възстановената база.

**Мониторинг:**
- **Uptime:** `/api/health` отговаря с 200 само докато приложението и базата му работят и на диска има място (виж
  стъпка 10).
- **Грешки:** Sentry, когато е зададен `SENTRY_DSN` (виж стъпка 9). Отчетите съдържат само мястото в кода и номера
  на профила; браузърът ги праща през приложението (`/api/monitoring`), никога директно към Sentry. За да не може бъг
  в цикъл (или някой с публичния DSN) да изразходва безплатния план (5000 на месец), отчетите на сървъра са до 20 на
  минута, а на браузърите — до 10 на минута и 150 на ден. Всичко е и в лога (`💥` за сървъра, `🧯` за браузърите).
- **Статистика за старта:** `/admin` → Статистика: активни играчи на ден, нови играчи (профили и гости), запазени
  гост-профили, мачове, линкове с предизвикателство, дневното предизвикателство и колко от новите играчи се връщат на
  следващия ден и след седмица. Брои се на сървъра в момента на събитията; без бисквитки, без проследяване, без
  трети страни.
- **Обновления:** Dependabot отваря седмични pull request-и за npm пакетите, базовия образ на Node, Caddy, Litestream
  и CI actions (поправките за сигурност — веднага); CI тества всеки от тях.

**Логове:** `docker compose logs -f -t app` (с ротация: 5 × 10 MB на контейнер).

Текущите мачове, опашките и стаите се държат в паметта, затова пускай само една инстанция на приложението.
