# АЛМАНАХ — almanac.bg

Десет въпроса на ден, едни и същи за цяла България. Всеки верен отговор в броя пише факт с мастило в твоя
Алманах, а печатът на всяка глава казва колко от нея държиш. Приятели, класация на деня и дуели, всеки по свое време.
Играй на **[almanac.bg](https://almanac.bg)**.

Свободен софтуер под [AGPL-3.0](LICENSE).

## Как е направена

Една програма на Go и уеб клиент на чист TypeScript и CSS, без рамки.

- **Сървърът** (`cmd/almanac`, `internal/`) е един статичен файл: HTTP, HTTPS, базата данни (SQLite), пощата и
  клиентът са вътре. Зависи само от драйвера за SQLite, от age, с който се шифроват резервните копия, и от
  golang.org/x/image, с който се рисуват картите за споделяне.
- **Клиентът** (`web/`) се строи с esbuild през `go run ./cmd/build`, който казва и колко е първият екран заедно със
  шрифтовете и какъв е бюджетът му (пазен в CI), а играта се изпитва в Chromium, WebKit и Firefox (`e2e/`).
  Шрифтовете (Sofia Sans, с българските форми на буквите) са наши файлове: браузърът не пита никой друг за нищо.
- **Въпросите** (`internal/bank`) са сърцето на играта: всеки вид въпрос (с избор, с число, за подреждане) сам се
  проверява, раздава и оценява. Нов вид е нов файл тук и неговият изглед в клиента.

```
cmd/almanac      програмата: serve, банката, копията, изтриване на играч (`almanac` без нищо изрежда командите)
cmd/build        строи клиента в internal/assets/dist
internal/bank    въпросите: видовете, банката на диска, проверките
internal/store   SQLite и миграциите (internal/store/migrations)
internal/account гости, вход с код по имейл, сесии, имена
internal/mail    пощата: опашка в базата, SMTP
internal/play    играта: броят, мастилото и печатите, главите, серията, приятелите, дуелите, класацията
internal/push    известията (Web Push)
internal/card    картинката на споделен ден и на сайта (PNG)
internal/backup  копията на базата в R2
internal/server  HTTP: API, страницата на приложението, файловете
deploy           услугата и скриптовете на сървъра
web/src          клиентът: lib/ (DOM, сигнали, рутер), game/ (въпросите, играта), screens/, ui.ts, fonts/
web/DESIGN.md    дизайнът: правилата (стойностите са в web/src/app.css)
e2e              играта в истински браузъри (Playwright)
bank/sample      публична извадка от въпросите (истинските са частни)
```

## Разработка

Нужни са Go и (само за проверките на клиента) Node 24.

```bash
go run ./cmd/build -watch            # клиентът, при всяка промяна
DEV=1 go run ./cmd/almanac serve     # http://localhost:8080 — пощата отива в лога
```

Проверки, както в CI:

```bash
go vet ./... && go test -race ./...
npm ci && npm run check && npm test
npm run e2e                          # играта в Chromium, WebKit и Firefox (BROWSER_PATH: свой Chromium)
go run ./cmd/almanac bank check      # банката в private/ (пада на каквото сървърът би отказал, на правилата ѝ и на баланса: cmd/almanac/bank.go)
go run ./cmd/almanac bank check -sample bank/sample   # извадката
```

Истинската банка е в частното хранилище `almanac-bg/almanac-questions`, клонирано в `private/`. Без нея играта
върви с извадката в `bank/sample`.

## Сървърът

Един сървър (Hetzner), зад Cloudflare. Програмата работи като systemd услуга (`deploy/almanac.service`) и сама
говори HTTPS със сертификата на Cloudflare за сървъра. На всеки 15 минути копира базата си в Cloudflare R2.

- Всяко сливане в `main`, което променя програмата, е ново издание: GitHub строи програмата, вдига версията (второто
  число, ако носи миграция, иначе третото) и я слага на сървъра (`.github/workflows/deploy.yml`).
- На сървъра `almanac-deploy vX.Y.Z` слага версията веднага: всяка игра е в базата, отговор по отговор, и рестартът
  не прекъсва игра. Щом `deploy/release-signers` назове ключ, приема
  програмата само с подписа на издаването. Версия, която носи промени в базата (миграции), първо я копира (`before-vX.Y.Z.db`);
  ако новата версия не отговори до три минути или спре в следващите две, се връща предишната, с базата отпреди нея.
  Същата команда с по-стара версия връща назад; към версия с по-малко второ число — само на ръка, по стъпките в
  `CLAUDE.md` („Production“), защото базата трябва да се върне отпреди миграцията. Версия, която вече работи, не се пипа,
  затова след всяко сливане GitHub иска последното издание и пускане, което не е минало, се опитва отново.
- Промените в `deploy/` стигат до сървъра само на ръка, както ги слага `deploy/setup.sh`; дотогава GitHub отбелязва
  пускането като неуспешно.
- Защитната стена на сървъра (`deploy/nftables.conf`) пуска към играта (порт 443) само адресите на Cloudflare, а към
  ssh (порт 22) всички, но вход има само с ключ (`deploy/sshd.conf`). Слага ги `deploy/harden.sh` (от `setup.sh`),
  след като ги провери; ако не бъдат потвърдени от нов вход с `almanac-harden confirm` до десет минути, всичко се
  връща както е било. Същите правила има и защитната стена на Hetzner пред сървъра (`deploy/hetzner-firewall.json`).
- Нови въпроси: `almanac-bank` — проверява новата банка отделно и едва тогава я дърпа и презарежда без рестарт.
  Сървърът играе свое копие на банката и ако тя има грешки, тръгва
  с последното добро копие.
- От копията на базата отпреди издание (`before-vX.Y.Z.db`) остават последните две, а всяко копие до базата
  (и старата база, оставена при възстановяване) се изтрива след месец.

### Резервни копия

На всеки 15 минути (в 7, 22, 37 и 52 минути след кръгъл час) сървърът копира базата в R2 (`internal/backup`): като
отделен процес с по-нисък приоритет, за да не взима от играта нито процесор, нито памет. Ако сървърът се загуби, се
губят най-много около 20 минути игра. Копието се проверява (`integrity_check`; празна база не се праща), компресира и
шифрова с [age](https://age-encryption.org) за ключ, който не е на сървъра. Всяко копие е нов обект с часа си
(`hours/2026-11-17T153012Z.db.gz.age`, пази се седмица), а първото за деня (UTC) отива и в `days/` (пази се месец):
сървърът не презаписва и не трие копия. Копието на деня веднага се сваля, разшифрова и проверява отново.

Всяко копие сравнява редовете на всяка таблица с тези в предишното и в първото за деня: таблица, която е загубила
половината си редове или ги е удвоила, е проблем, докато копията отпреди това още са тук. Веднъж на ден се проверява
и че никой ред не сочи към ред, който го няма (`foreign_key_check`). Каквото не е наред (неуспешно копие, липсващ ключ,
стари копия, които R2 не е изтрил, или копия, изтрити твърде рано, рязка промяна в редовете) идва на `ALERT_EMAIL`
веднъж на ден.

**Ключът, веднъж.** На своя компютър, не на сървъра: `go run ./cmd/almanac backup keys` (или `age-keygen -pq`).

- Тайният ключ (`AGE-SECRET-KEY-PQ-1…`) се пази **само извън сървъра**: в мениджъра на пароли и още веднъж на
  хартия или флашка. Без него никое копие не може да се отвори. На сървъра не бива да попада: който пробие сървъра,
  би прочел с него и всички копия.
- Публичният (`BACKUP_RECIPIENT=age1pq1…`) отива в `/etc/almanac/env` и влиза в сила при следващото издание (или
  `systemctl restart almanac`). Без него копията се пращат нешифровани, както преди, и сървърът напомня всеки ден.

**R2, веднъж, в таблото на Cloudflare** (R2 → кофата `almanac-backups` → Settings):

1. *Object lifecycle rules* → Add rule: префикс `hours/`, изтриване след 7 дни; второ правило: префикс `days/`,
   изтриване след 30 дни. Така копията живеят колкото казва страницата за поверителност, а старите имена
   (`hours/07.db.gz`, `days/17.db.gz`) изчезват сами. Ако R2 трие копията в `hours/` по-рано, сървърът казва и това.
2. *Bucket lock rules* → Add rule: префикс `hours/`, задържане 7 дни; второ: префикс `days/`, задържане 30 дни.
   Докато трае, никой не може да изтрие или подмени копие, дори с ключа на сървъра.
3. R2 → *Manage API tokens* → Create: *Object Read & Write*, само за кофата `almanac-backups`, с *Client IP
   filtering* само за адресите на сървъра. Новите ключове — в `BACKUP_ACCESS_KEY` и `BACKUP_SECRET_KEY`, после
   старият токен се изтрива. За своя компютър: отделен токен *Object Read only* за същата кофа, пазен до тайния ключ.

**Проверка и възстановяване.** Командите на сървъра искат неговите настройки:

```bash
alias almanac-backup='systemd-run --pipe --wait --quiet --collect -p User=almanac -p EnvironmentFile=/etc/almanac/env /usr/local/bin/almanac backup'
almanac-backup list                       # копията, най-новото отгоре
almanac-backup verify                     # последното копие на деня: цяло ли е, както е пратено, и от този сървър ли е
systemctl stop almanac.socket almanac
almanac-backup restore -identity - -into-place -confirm ИМЕ ИМЕ   # ИМЕ от list, два пъти; поставяш тайния ключ, Enter, Ctrl-D
systemctl start almanac.socket almanac
```

`-into-place` отказва, докато играта работи; сваля копието, проверява го, показва името му, кога е качено и колко реда
има и го слага само ако името е потвърдено: с `-confirm ИМЕ` (преди името: след него флаговете не се четат) или, без
него, написано в терминала, който пита. `systemd-run --pipe` не дава такъв терминал, затова горе е с `-confirm`.
Оставя старата база до новата (`replaced-….db`, с нейния `-wal`; изтрива се след месец) и маха `-shm`.

`verify` и възстановяването във файл (`restore -identity - ИМЕ нов-файл.db`) приемат вместо име и `latest`: само
шифровано копие, наречено и качено така, както ги прави сървърът. Каквото друго е по-ново (нешифровано, с друго име,
качено много след часа в името си) се прескача и се изписва: някой с ключа на кофата може да е сложил там свое копие.
Нешифровано копие (отпреди шифроването или от сървър без `BACKUP_RECIPIENT`) се възстановява само нарочно: с името му
и `-unencrypted`, никога като `latest`. Само с age (1.3 или по-нов): `age -d -i ключ.txt копие.db.gz.age | gunzip >
almanac.db`.

**Изтриване на играч** по негова молба по поща, със същите настройки:
`systemd-run --pipe --wait --quiet --collect -p User=almanac -p EnvironmentFile=/etc/almanac/env /usr/local/bin/almanac player delete ИМЕЙЛ`
(или `@потребителско-име`) казва кой е и какво пази базата за него, без да променя нищо; с `-yes` преди имейла го
изтрива. Без настройките командата не намира базата и отказва.

### Нов сървър и каквото е извън кода

Стъпките, в този ред. Стойностите не са тук: те са в мениджъра на пароли на собственика и в конзолите.

1. **Сървърът** в Hetzner Cloud (console.hetzner.cloud): ARM (изданията са само `linux-arm64`), Ubuntu, ключът на
   собственика за root, резервните образи на Hetzner (*Backups*) включени. Защитната стена на Hetzner пред него е
   `deploy/hetzner-firewall.json`: `hcloud firewall replace-rules СТЕНА --rules-file deploy/hetzner-firewall.json`, после
   `hcloud firewall apply-to-resource СТЕНА --type server --server СЪРВЪР` (или същите правила на ръка в конзолата).
2. **Ключ на root за въпросите:** `ssh-keygen -t ed25519` като root, публичната част като deploy key само за четене
   на `almanac-questions` в GitHub. Без него `setup.sh` не може да изтегли банката.
3. **`deploy/` на сървъра** (`scp -r deploy root@АДРЕС:`) и като root `sh deploy/setup.sh`, после
   `almanac-harden confirm` от нов вход до десет минути (иначе защитната стена и ssh се връщат сами).
4. **Настройките:** `/etc/almanac/env` и `/etc/almanac/origin.pem`/`origin.key` от мениджъра на пароли, всеки с
   `install -o root -g almanac -m 640`. Каквото липсва там, е описано в `deploy/env.example`; в него `MTA_STS_MODE` е
   `testing`, а в играта е `enforce`.
5. **R2:** токенът на сървъра (R2 → *Manage API tokens*) пуска само адресите в своя *Client IP filtering*: добави
   новите адреси (IPv4 и IPv6) там, преди да възстановяваш, иначе сървърът не стига до копията. Старите се махат,
   щом старият сървър го няма.
6. **Първото пускане:** `almanac-deploy vX.Y.Z` (последното издание) на ръка. Тръгва на празна база, която не се
   праща никъде. На ръка, не от CI: издание, което не тръгне, CI не пуска пак.
7. **Ключът на CI:** в `/root/.ssh/authorized_keys` редът, който дава `deploy/deploy-ci.sh` (най-горе в него), с
   публичната част на тайната `DEPLOY_KEY` (средата `production` в GitHub): от стария сървър, а ако я няма, нова
   двойка (`ssh-keygen -t ed25519 -N '' -C almanac-ci-deploy -f ci-deploy`, частната с
   `gh secret set DEPLOY_KEY --env production < ci-deploy`, после двата файла се изтриват). Адресът на сървъра и
   ключът на хоста са в `.github/workflows/deploy.yml` (стъпката „The server's key“: `known_hosts` и `HostName`): новите
   (`ssh-keyscan -t ed25519 АДРЕС`) влизат там със сливане в `main`.
8. **Преминаването:** на стария сървър, ако още върви, `systemctl stop almanac.socket almanac` и `almanac-backup now`
   (последното копие); на новия спиране, възстановяване на най-новото копие и пускане, както горе.
9. **DNS накрая**, в Cloudflare: записите A и AAAA на `almanac.bg`, `www` и `mta-sts` към новите адреси, през
   Cloudflare (*Proxied*). Готово е, когато `https://almanac.bg/api/health` показва версията и `"ok":true`. Мониторите
   на Better Stack гледат името, не адреса: не се пипат.

**Cloudflare** (dash.cloudflare.com, зоната `almanac.bg`), каквото не е в кода: *SSL/TLS* в режим *Full (strict)*,
най-малко TLS 1.2, *Always Use HTTPS* (HSTS идва от програмата); сертификатът за сървъра е *Origin Server* (той е
`origin.pem`/`origin.key`); правилото за пренасочване `www` → `almanac.bg`; правилото за честота на заявките
(*Security → WAF → Rate limiting rules*) пред входа и гостите; кофата `almanac-backups` в R2 (горе). DNSSEC е включен
в Cloudflare (*DNS → Settings*); записът DS, който Cloudflare дава там, се поставя при регистратора (Register.BG).
**Преди DNS да се премести от Cloudflare, DS се маха при регистратора** и се чака да изтече: иначе името спира да се
отваря за всеки, който проверява подписите.

**Пощата.** Излиза през Scaleway TEM (console.scaleway.com: домейнът `almanac.bg` и ключът в `SMTP_URL`, който има
срок, видим там), влиза в Proton (privacy@, abuse@, postmaster@). Записите ѝ са в зоната на Cloudflare и не зависят
от сървъра: MX, SPF, DKIM (на Proton и на Scaleway), DMARC, `_mta-sts` и `_smtp._tls`, CAA и записите за потвърждение
(Google, Proton, GitHub). Ако зоната някога се мести, първо *DNS → Records → Export*: оттам се правят наново.

**Тайните извън сървъра.**

- `/etc/almanac/env` и `origin.key`/`origin.pem`: в мениджъра на пароли, обновявани там при всяка промяна. Без
  `PUSH_PRIVATE_KEY` известията спират за всички.
- Тайният ключ на копията: в мениджъра на пароли и още веднъж на хартия или флашка (горе).
- `DEPLOY_KEY` и `RELEASE_SIGNING_KEY`: само в средата `production` в GitHub. Загубен се прави наново: първият както
  в стъпка 7, вторият както казва `deploy/release-signers`.
- Ключът на сървъра за въпросите: само на сървъра, нов с всеки сървър (стъпка 2).
- Профилите в Hetzner, Cloudflare, Register.BG, Scaleway, Proton, Better Stack и GitHub: на собственика, с вход в
  мениджъра на пароли.

### Наблюдение

Отвътре сървърът казва каквото намери (неуспешно копие, малко място на диска, база, която не приема запис, поща, която
не излиза, отказани известия, липсващи настройки, въпроси за дните напред, които свършват) по имейл (`ALERT_EMAIL`). Но писмото минава през същата база и същата поща, а спрял сървър не казва нищо, затова отвън (Better
Stack):

- **Сървърът**: `https://almanac.bg/api/health` всяка минута, с ключова дума `"ok":true`. Отговорът е 503, ако базата
  не приема запис (пробва се на 30 секунди), и съдържа `"disk":"low"`, когато дискът е под 15% или под три бази, и
  `"mail":"failing"`, когато пощата не излиза: втори монитор на същия адрес, който вдига тревога, ако ги съдържа, хваща и
  тях.
- **Копията**: `BACKUP_HEARTBEAT` се вика след всяко копие (на 15 минути); мониторът вдига тревога, ако не го чуе час.

## In English

ALMANAC (АЛМАНАХ) is a Bulgarian quiz game at [almanac.bg](https://almanac.bg): ten questions a day, the same for
everyone in Bulgaria; each right answer writes its fact in ink in your book, and each chapter's seal says how much of it
you hold; friends, the day's board and duels in each one's own time. One Go program (the standard library, a pure-Go
SQLite driver, age and x/image) serves a plain TypeScript client with no framework. Run it with `go run ./cmd/build &&
DEV=1 go run ./cmd/almanac serve`. Free software under the AGPL-3.0; issues and pull requests in English are welcome.
